# unikraft-gleam

A [Wisp](https://gleam.run/gleam-http/wisp/) HTTP server written in
[Gleam](https://gleam.run/), served by [Mist](https://hexdocs.pm/mist/), running
as a Unikraft unikernel on **both architectures**.

```sh
./build.sh                    # host arch; or: ./build.sh x86_64
bsdkrun unikraft . --mem 1024 --port 3000:3000 --cmdline \
  "elfloader -- /erl/erts/bin/beam.smp -fnu -- -root /erl -bindir /erl/erts/bin \
   -progname erl -- -home /root -- -noshell -eval wisp_demo@@main:run(wisp_demo) --"
```

## Status

**arm64 works**, verified on macOS/Hypervisor.framework:

```console
$ curl localhost:3000/
Hello from Gleam on Unikraft!
$ curl localhost:3000/info
{"runtime":"gleam","gleam":"1.18.0","otp":"29","erts":"17.0.4"}
$ curl -o /dev/null -w '%{http_code}\n' localhost:3000/nope
404
```

x86_64 has never been run; `.github/workflows/e2e-unikraft-examples.yml` builds
and boots it, non-strict, and that job is the test.

Nothing new was needed in Unikraft. Gleam is a BEAM language, so the one fix
[`../unikraft-elixir`](../unikraft-elixir) turned up — patch 17, a leading
zero-length `iovec` entry failing the whole `writev()` with `EIO`, which is how
Erlang's inet driver always writes — is what makes this one able to send a
response as well. Without it the boot completes, the listener comes up, the
request is read, and the connection closes with nothing on it.

## Gleam is a BEAM language, so this is ../unikraft-elixir with a different front end

Gleam compiles to Erlang. The Kraftfile here and the one in
[`../unikraft-elixir`](../unikraft-elixir) differ only in how the emulator is
entered, and the arm64 fix that example needed — a leading zero-length `iovec`
entry failing the whole `writev()` with `EIO`, which is how Erlang's inet driver
always writes — is what makes this one serve a response too. It is patch 17 in
[`../../library/unikraft-base/patches/apply.sh`](../../library/unikraft-base/patches/apply.sh).

What is different is everything around the emulator, because Gleam has no
releases.

## No shell, so no `entrypoint.sh`

`gleam export erlang-shipment` writes a directory per application and a
generated `entrypoint.sh` whose real content is one command:

```sh
exec erl \
  -pa "$BASE"/*/ebin \
  -eval "$PACKAGE@@main:run($PACKAGE)" \
  -noshell \
  -extra "$@"
```

A unikernel has no shell and runs exactly one program, so that has to become
the single `execve` at the end of it. Replacing the emulator with a script that
prints its own arguments is the way to find out what that is:

```sh
B=$(echo /usr/local/lib/erlang/erts-*/bin)
mv "$B/beam.smp" "$B/beam.smp.real"
printf '#!/bin/sh\nfor a; do echo "$a"; done\n' > "$B/beam.smp"
chmod +x "$B/beam.smp"
sh build/erlang-shipment/entrypoint.sh run
```

Doing that prints **21 `-pa` arguments** — one per application in the shipment,
and it grows with every dependency added. That does not belong on a kernel
command line, so `ERL_LIBS=/srv` replaces the lot: it adds `<dir>/*/ebin` to the
code path, which is exactly the shape a shipment already has. The variable is
compiled into the image through `CONFIG_LIBPOSIX_ENVIRON_ENVP8`, next to the
four (`ROOTDIR`, `BINDIR`, `EMU`, `PROGNAME`) that `erlexec` would have
exported. `BINDIR` is not optional — without it beam.smp prints

```
Environment variable BINDIR is not set
```

and exits before opening a single file.

`@@main:run/1` is generated by the Gleam compiler: it sets up the standard I/O
encodings, starts the application, and calls `main`. Since `main` ends in
`process.sleep_forever()`, it never returns — which is what a unikernel needs,
because when the program returns the guest powers off.

### The boot scripts have to come across

A mix release names its own boot script, so the Elixir example never touches
`$ROOTDIR/bin`. A shipment has no boot script at all, so the emulator falls
back to its default, `$ROOTDIR/bin/start.boot`, and without it the guest dies
before Gleam runs:

```
Runtime terminating during boot ({'cannot get bootfile','/erl/bin/start.boot'})
```

The Dockerfile copies `$ERL/bin/*.boot`; they are a few kilobytes.

### The command line must end in `--`

libkrun appends its own hints (`earlycon=`, `virtio_mmio.device=`) after
whatever command line it is given, and they arrive as `argv`. The BEAM's
argument parser would otherwise fold them into the last flag it saw, so the
vector ends with a bare `--`: everything past it is a plain argument that
nothing in this program reads.

## Architecture

Neither stage names a library path. `ldd` is asked instead — over the emulator,
the helper programs, and the NIFs under `lib/*/priv`, which are `dlopen`ed and
drag in OpenSSL — so each architecture gets what it actually needs:
`/lib/aarch64-linux-gnu/…` with `/lib/ld-linux-aarch64.so.1` on one,
`/lib/x86_64-linux-gnu/…` with `/lib64/ld-linux-x86-64.so.2` on the other. That
is a different directory *and* a different loader filename, which is why the
hardcoded lists in the upstream Unikraft Cloud examples cannot be ported by
substitution.

The build also splits by platform:

| stage     | platform          | produces                                          |
|-----------|-------------------|---------------------------------------------------|
| `build`   | `$BUILDPLATFORM`  | the shipment — `.beam` bytecode and `.app` files  |
| `runtime` | `$TARGETPLATFORM` | ERTS, the OTP applications, the shared libraries  |

Erlang bytecode is architecture-independent, so compiling it under emulation
would be waste. Both stages use the same image, which is also what keeps the
compiler and the emulator on one OTP version.

## What ships in the image

A shipment has no `.rel` file to read the required OTP applications out of —
that is a release concept — but every `.app` file names its own dependencies,
so the Dockerfile walks that graph to a fixed point. Six applications come out:

```
asn1  crypto  kernel  public_key  ssl  stdlib
```

`crypto` arrives through `gleam_crypto` (Wisp signs cookies with it) and `ssl`
through `glisten`; `public_key` and `asn1` are `ssl`'s own dependencies. The
other ~30 applications in `/usr/local/lib/erlang/lib` — `wx`, `megaco`,
`dialyzer`, `common_test` — stay behind, as do every `src`, `doc`, `examples`,
`man` and `include` directory, and everything in `erts-*/bin` except
`beam.smp`, `erl_child_setup` and `inet_gethost`.

The result is a 50 MiB root filesystem. That matters more than usual: it is
embedded in the kernel image *and* unpacked into a RAM filesystem at boot, so
it is resident twice before the BEAM allocates anything.

## Libraries that switch on the operating system see one they have never met

Wisp writes a temporary file per request and asks the `directories` package
where to put it. That package asks `platform.os()`, which on this guest answers
`unikraft` — so it printed

```
[WARN][directories] Operating system 'unikraft' is not supported by this library
```

once per request. `tmp_dir()` checks `TMPDIR`, `TEMP` and `TMP` before it ever
asks, so `CONFIG_LIBPOSIX_ENVIRON_ENVP9` in the Kraftfile takes the early exit.
Naming the directory at build time is also simply correct here: a unikernel's
filesystem is fixed when the image is built.

Worth knowing when adding dependencies — a package that dispatches on the OS
name has no branch for this one, and how gracefully it degrades is up to the
package.

## One line of noise at boot

```
=ESOCK WARNING MSG==== [UNIX-ESSIO] Failed open sctp dynamic library: libsctp.so.1
```

OTP's socket layer probes for SCTP by `dlopen`ing it by name, which is why
`ldd` cannot see the dependency and the resolution step above does not pick it
up. Nothing here speaks SCTP. Carrying a library solely to silence a probe is
the wrong trade in an image that is resident twice, so the warning stays.

## `--cmdline` is required

bsdkrun does not read the Kraftfile's `cmd` for a locally-built kernel, so the
program to run has to be given explicitly. The format is

```
<argv0> -- <application argv>
```

and everything before `--` is parsed as kernel library parameters, with the
first word skipped — see the [ExpressJS
README](../unikraft-expressjs/README.md) for why the placeholder is not
optional.
